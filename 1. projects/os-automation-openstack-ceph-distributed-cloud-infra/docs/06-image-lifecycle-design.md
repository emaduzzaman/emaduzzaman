# Image Lifecycle Design

This document describes the lifecycle management strategy for operating system images generated by the OpenStack Image Factory.

The lifecycle defines how images are:

- created
- versioned
- published
- consumed
- deprecated
- removed

A well-defined lifecycle ensures that users always receive updated images while maintaining safe rollback options.

---

# Image Lifecycle Overview

The lifecycle of an image passes through several stages.

```

Acquire Base Image
│
▼
Build Golden Image
│
▼
Validation
│
▼
Publish to Glance
│
▼
Tag as Current
│
▼
User Deployment
│
▼
Deprecation
│
▼
Removal

```

Each stage ensures that images remain reliable and manageable over time.

---

# Stage 1 — Base Image Acquisition

The lifecycle begins with acquiring an upstream cloud image.

Examples include:

- Ubuntu cloud images
- Debian cloud images
- Rocky Linux cloud images
- AlmaLinux cloud images

These images are imported into Glance as **base images**.

Example:

```

ubuntu-24.04-base

```

These base images remain unchanged and act as the starting point for the automated build pipeline.

---

# Stage 2 — Image Build

The image factory automation pipeline creates a new image from the base image.

The build process performs:

- system updates
- security patch installation
- package installation
- system configuration
- system cleanup

This stage produces a **golden image**.

Example naming format:

```

ubuntu-24.04-2026-03-10-1724

```

The timestamp indicates when the image was generated.

---

# Stage 3 — Image Validation

After the image is created, validation ensures it is safe for deployment.

Validation may include:

- successful VM boot test
- SSH accessibility verification
- cloud-init completion
- network functionality
- system package update status
- guest agent verification

Example validation commands:

```

cloud-init status
apt list --upgradable
systemctl status ssh

```

If validation fails, the image should not be promoted.

---

# Stage 4 — Image Publication

Once validation is complete, the image becomes available for general use.

The image is published to **OpenStack Glance** with metadata and tags.

Example metadata:

```

os_distro=ubuntu
os_version=24.04
build_method=packer
purpose=golden-image

```

Example tags:

```

ubuntu
24.04
golden
automated

```

These tags help identify the image during deployment.

---

# Stage 5 — Current Image Tagging

To simplify user deployments, the latest validated image can be marked as the **current production image**.

This can be done through:

- image tags
- alias naming
- metadata flags

Example alias:

```

ubuntu-24.04-current

```

When a new image is built, the alias may be updated to point to the latest build.

This ensures users always launch the newest stable image.

---

# Stage 6 — Image Consumption

Users deploy virtual machines using the golden image.

Typical deployment flow:

```

User selects image
│
▼
Cinder creates boot volume
│
▼
Volume stored in Ceph
│
▼
Nova boots instance

```

The resulting VM inherits the configuration prepared by the image factory.

---

# Stage 7 — Image Deprecation

Older images should eventually be deprecated.

Deprecation helps:

- prevent accidental use of outdated images
- reduce confusion among users
- improve security posture

Possible deprecation policies:

- mark images as deprecated after 30 days
- retain the last two versions
- notify users of replacement images

Example metadata:

```

deprecated=true

```

---

# Stage 8 — Image Retention

A retention policy defines how many images should be preserved.

Example strategy:

| Image Type | Retention Policy |
|-------------|----------------|
| Current image | Always retained |
| Previous version | Retained for rollback |
| Older versions | Removed after defined period |

Example retention rule:

```

Keep last 3 images per OS version

```

This ensures rollback capability without accumulating excessive storage.

---

# Stage 9 — Image Removal

Images that exceed the retention window can be removed.

Removal involves:

- deleting the Glance image
- removing the corresponding Ceph RBD object

Example cleanup:

```

openstack image delete <image-id>

```

Removing old images helps maintain efficient storage usage.

---

# Image Versioning Strategy

Images are versioned using timestamps.

Example:

```

ubuntu-24.04-YYYY-MM-DD-HHMM

```

Advantages:

- deterministic ordering
- easy identification of build time
- natural chronological sorting

Example builds:

```

ubuntu-24.04-2026-03-10-1724
ubuntu-24.04-2026-03-17-0200
ubuntu-24.04-2026-03-24-0200

```

---

# Lifecycle Design Benefits

The lifecycle model provides several advantages.

### Consistency

Every image is generated using the same repeatable pipeline.

### Security

Images are updated regularly with the latest security patches.

### Operational Efficiency

Administrators no longer need to manually rebuild images.

### Controlled Rollback

Older images remain available for safe rollback.

### Storage Optimization

Retention policies prevent unnecessary storage consumption.

---

# Summary

The image lifecycle design ensures that operating system images in the OpenStack environment remain:

- up-to-date
- validated
- versioned
- manageable
- storage efficient

By combining automated builds with lifecycle management policies, the system behaves similarly to public cloud image pipelines while remaining fully self-managed within the OpenStack environment.
